## Non-Negotiable Invariants

1. **Strict Scope Integrity**:
   Never implement features outside defined specifications without explicit approval. Features out of scope (e.g. 3-way AST token diffing, OCR parsing, embedding serving) must never be added.
2. **Tenant Boundary Isolation**:
   Every database query, cache key, and manifest operation must enforce hard multi-tenant isolation using `tenant_id`.
3. **Mandatory Doc API Synchronization**:
   > **The API documentation ("Doc API") must ALWAYS be updated no matter how little the created or modified code is.**
   > Every addition, modification, or removal of externally exposed gRPC RPCs, Protobuf messages, HTTP routes, or OpenAPI endpoints must be documented in `api/openapi/openapi.yaml` and Protobuf comments in the exact same changeset. Internal repository port contracts must be documented directly at their Go interfaces. See `.ai/doc-api.md` for full specifications and workflows.
4. **Strictly Secured Logging**:
   > **All logging must be strictly secured.**
   > Emit structured JSON with `trace_id` and `tenant_id`. All authorization tokens, credentials, and API keys must be redacted. Raw document chunk texts and user prompts must NEVER be logged (log only safe SHA-256 hashes, chunk IDs, and token counts).
5. **Robust & Sanitized Error Handling**:
   Wrap errors with actionable domain context internally. Sanitize client-facing responses: never leak internal stack traces, raw SQL queries, or database schema details to callers.
6. **Testing & Quality Assurance**:
   Unit tests (`test/unit/`) and integration tests (`test/integration/`) against PostgreSQL 16 and Redis 7.2 must be maintained and pass with `-race` enabled before declaring any work complete.
7. **Bounded Memory & Zero-cgo Runtime**:
   The primary gRPC ingress path must remain pure Go (zero cgo). Enforce explicit in-flight byte and per-buffer size limits independent of `sync.Pool` (which serves strictly as an allocation reuse optimization). Total pod RSS must be validated under stress to remain strictly below the $1.2\text{ GiB}$ target, with the $1.5\text{ GiB}$ container limit serving only as an outer safety cap.

## Human-in-the-Loop Rules

- Always propose an implementation plan or prompt in `prompts/<task-name>.md` and obtain user approval before writing code.
- Stop and prompt for human review whenever encountering ambiguity, architectural pivots, or destructive actions.
- Provide clear verification steps, test output, and proof of correctness after completing any unit of work.

---

## Pre-Commit Rules

Before committing code, opening a pull request, or marking a task complete:

1. Format code and optimize imports: `goimports -w .`
2. Run static analysis: `golangci-lint run --timeout=5m` (zero lint errors required).
3. Verify test suites: `go test -v -race ./test/unit/...` and relevant integration tests.
4. Audit security: Run `govulncheck ./...` and verify zero unredacted log emissions.
5. **Verify Doc API**: Ensure `api/openapi/openapi.yaml` and Protobuf schemas match all code changes.
6. Update `.ai/progress-tracker.md` with completed items and architectural updates.

## Git Commit Standards
- **Git Commit Frequency**: Commit code as you build. Every working session or phase must contain **at least two git commits**.
- **Conventional Commit Patterns**: All git commit messages must strictly adhere to the following prefixes:
  - `feat:` for new features 
  - `fix:` for bug fixes
  - `refactor:` for code refactoring
  - `docs:` for documentation updates
  - `tests:` for tests addition and modification
  - `chore:` for maintenance tasks and environment setup
